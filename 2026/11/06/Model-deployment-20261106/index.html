深度学习模型的端侧部署&推理加速

发表于2026-11-06|更新于2026-11-06|机器人
|总字数:4.6k|阅读时长:13分钟|浏览量:

事情的起源是我们训练好了一个网络，只是替换了一下某个模块的模型（onnx），然后再转化为了hbm，明明其他的模块也是用相同的转化方式，其他模块用起来没问题，但是这个新替换的模块加入之后效果不增反减。 再经历了反复的检查，测试，才发现，问题居然出现在模型的转换上。原本以为模型格式都是固定的数学转换，没想到有很多内容呀！

引言

在电脑上训练好一个深度学习模型，只是机器人应用落地的其中一步。真正装到机器人上以后，它还要面对有限的算力、内存和电量，以及持续变化的环境。

模型部署要做的，就是让训练好的神经网络在目标硬件上正确、高效、稳定地执行推理，并接入机器人的感知、决策或控制流程。 从 PyTorch 到 ONNX，从量化到 NPU，再到 C++ 和 ROS2，这些看起来分散的名词，其实都围绕着这件事展开。下文的内容按照下图的步骤展开。

一、模型部署

首先，简要来说，训练是通过数据学习模型参数，推理是利用已有参数处理新的输入。部署则负责为实际设备准备模型和运行环境，并把推理能力接入应用。

一个典型的机器人模型开发流程，可以分成五个阶段：

  1. 数据采集与模型训练：准备数据，在训练框架中获得模型参数。
  2. 模型导出与验证：导出适合部署的模型表示，检查输入输出是否符合预期。
  3. 模型优化与硬件适配：根据目标芯片的能力，进行编译以及必要的精度、结构优化。
  4. 板端运行与系统集成：完成前处理、推理和后处理，接入机器人软件系统。
  5. 实机测试与迭代：验证任务效果、时延、资源占用和长期稳定性。

本文关注的主要是第 2～4 步，以及紧随其后的验证工作。文章标题的端侧部署，指模型运行在机器人本地的嵌入式计算设备上。

可以把这台设备理解为机器人身体里的“小电脑”，第 3 步的目标芯片就是其中负责计算的核心部件。**机器人 SDK（软件开发工具包）**则是厂家提供的一套现成软件工具，让程序方便地读取机器人状态、发送动作指令，主要用于第 4 步的系统集成。

例如：模型在 RK3588 上识别出障碍物，避障程序据此决定停车，再通过机器人 SDK 发送停车指令。

部署需求也会反过来影响训练：芯片支持哪些算子、允许多大的模型、需要多快的响应，都适合在模型设计时提前考虑。

二、1-3步

1. .pt：保存训练得到的模型信息

.pt、.pth 是 PyTorch 中常见的保存文件后缀。文件里可能是模型参数，也可能包含模型对象或训练检查点；如果只保存了参数，恢复模型时还需要对应的网络结构。具体内容取决于保存方式，不能仅凭后缀判断。参见 PyTorch 模型保存与加载说明。

  • FP32、FP16 描述的是数据的数值表示，同样以 .pt 结尾的文件，可以保存不同精度的数据。

2. ONNX

ONNX 是一种开放的模型交换格式。它可以理解为神经网络模型的“通用交换格式”。它用统一的方式描述网络结构、模型参数以及输入输出，方便不同工具读取和处理。

可以把这一步理解为：把训练框架中的网络计算逻辑，整理成其他工具能够识别的表达形式。

但导出成功只是第一步。目标工具链还需要支持模型使用的算子、数据类型、输入形状和 ONNX 算子版本。通用格式并不意味着可以在所有芯片上直接运行。

导出以后，通常会先使用 ONNX Runtime 等推理引擎，在相同输入下对照原模型的输出，确认转换没有引入明显偏差。

3. Netron可视化

Netron 是模型结构可视化工具，可以打开 ONNX 等模型文件，查看计算图和张量信息。如下图所示：

图中的 Convolution 是卷积，负责提取特征；BatchNorm 是批量归一化；ReLU 提供非线性变换；MaxPool 降低特征图的空间分辨率；Add 则表示逐元素相加，常见于残差连接。

部署时，尤其需要关注模型要求的输入尺寸、颜色通道、张量布局，以及输出的含义。这些信息决定了前后处理应该怎样组织数据。

例如：输入形状为 [1, 3, 640, 640]，在 NCHW 布局下表示 1 张图像、3 个通道、640×640 的分辨率。板端送入的数据要符合这一约定。

Netron 适合检查结构；模型结果是否正确，还需要通过实际推理和输出对比来验证。

三、硬件适配

不同芯片支持的计算指令、数据类型和内存组织方式不同，因此常常需要通过对应的工具链，把模型转换或编译为适合目标设备执行的形式。

下面是几类常见的部署生态，文件后缀仅用于帮助识别，具体格式仍以对应平台和工具链为准。

部署生态 常见模型文件 主要计算硬件
RKNN .rknn 瑞芯微 NPU
TensorRT 序列化 Engine，常见后缀为 .plan NVIDIA GPU
地平线工具链 .bin、.hbm 等 地平线 BPU
寒武纪工具链 部分流程使用 .cambricon 离线模型 寒武纪 MLU

这些工具通常会进行算子融合、内存规划和计算调度，并选择适合硬件的计算方式。其中，算子融合可以把一些相邻操作合并执行，减少中间数据搬运和调用开销。

还要区分转换工具和运行时：前者负责准备模型，后者负责在设备上加载和执行模型。RKNN-Toolkit2 与 RKNN Runtime 分别承担这两类职责；寒武纪的 CNRT 指运行时库，不能把它当成整套模型转换工具链的名称。参见 CNToolkit 组件说明。

例如：同一个视觉模型，部署到 RK3588 时可以走 RKNN 流程，部署到 NVIDIA Jetson 时可以走 TensorRT 流程；两者生成的模型文件不能直接互换。

模型能否运行还受到芯片型号、驱动、转换工具和运行时版本的共同影响。转换完成后，需要在实际目标设备上验证兼容性和性能。

四、量化与剪枝

✍️重点来了！！！！！！

模型优化的目标，是在满足任务效果的前提下，降低计算、存储或功耗开销。量化和剪枝都是常见手段，是否采用要由实际测量结果决定。

1. FP32、FP16 与 INT8

数值表示 含义 单个数值的存储大小
FP32 32 位浮点数 4 字节
FP16 16 位浮点数 2 字节
INT8 8 位有符号整数 1 字节

FP16 仍属于浮点表示，而常见的 INT8 量化会把浮点值映射到有限的整数范围。映射过程通常涉及缩放、舍入和截断，因此会产生量化误差。

例如：1000 万个参数，全部按 FP32、FP16、INT8 存储时，原始参数量分别约为 40 MB、20 MB、10 MB。这里没有计算中间张量、元数据和运行时开销。

较低精度有机会减少存储和数据搬运，并利用硬件上的低精度计算单元。但文件变小，不代表推理一定更快：算子支持、精度转换开销和硬件实现都会影响最终收益。参见 ONNX Runtime 量化说明。

2. PTQ

PTQ（Post-Training Quantization，训练后量化）通常不需要重新训练，适合在已有模型上尝试低精度部署。

常见的静态量化和动态量化，主要区别在于：模型中间计算结果，也就是激活值，其量化参数在什么时候确定。

静态 PTQ 会提前用校准数据运行模型，统计激活值的分布，确定量化参数。实际推理时，使用已经确定的参数。

校准集的重点是具有代表性，要尽量接近实际使用时的数据分布。“100 张图像”只是可能的示例，合适的样本量需要结合任务和工具链验证。最终测试集应独立保留，用来评估量化后的真实效果。

例如：用于室内避障的视觉模型，校准图像应覆盖明亮、昏暗、近距离障碍物等情况，只用一种光照下的图片容易遗漏实际场景。

动态 PTQ

模型训练完成后，神经网络的权重和偏置等参数通常已经固定。每当接收到一个新的实时输入时，模型利用这些固定参数执行前向传播，包括线性运算和非线性运算，产生各层的激活值和最终输出。

为了降低推理时的计算和存储开销，可以采用 INT8 量化。动态 PTQ 通常提前量化固定的权重，而对于需要量化的激活张量，在推理时根据它的当前数值分布，动态计算 Scale（缩放因子）、Zero Point（零点）等量化参数，使其能够更合理地映射到低精度整数范围，从而控制量化误差，并利用硬件支持的低精度计算进行加速。

动态计算量化参数也会引入额外开销，实际能否加速仍需测量。静态与动态量化的支持范围和效果取决于推理引擎、模型与硬件。参见 静态与动态量化的区别。

3. QAT

QAT（Quantization-Aware Training，量化感知训练）会在训练或微调时引入模拟量化，让模型提前适应低精度表示带来的误差。

常见做法是加入 Fake Quantization，也就是“伪量化”：前向计算模拟量化及反量化的数值影响，参数更新通常仍在浮点表示下进行。训练完成后，再转换成目标工具链支持的量化模型。参见 PyTorch 对 QAT 的解释。

对比维度 PTQ QAT
是否需要训练或微调 通常不需要 需要
应对量化误差的方式 调整校准与量化策略 训练时让参数适应误差
开发成本 较低 较高
常见使用时机 建立量化部署基线 PTQ 的任务精度仍不满足要求

工程上可以先评估 PTQ。如果精度下降明显，先检查预处理、校准数据和量化策略，再考虑保留部分层的较高精度，或引入 QAT。QAT 模拟的量化方式也需要与实际部署方式相匹配。

4. 剪枝

剪枝通过移除部分参数或网络结构，尝试降低模型开销。常见方式有两类：

  • 非结构化剪枝：把部分权重置零。能否加速，取决于硬件和推理引擎是否支持相应的稀疏计算。
  • 结构化剪枝：删除整个通道、卷积核或其他结构，更容易减少常规计算量，但通常需要微调来恢复任务精度。

量化和剪枝都需要重新评估任务效果。如果原模型已经满足板端需求，就没有必要为了使用某项技术而增加部署复杂度。

五、板端运行

得到专用模型文件以后，还需要把它组织成一条完整的数据处理链路：

传感器数据 → 前处理 → 模型推理 → 后处理 → 机器人其他模块。

C++ 常用于实现这条链路，因为它便于调用硬件接口、管理内存，并与现有机器人程序集成。具体语言仍应根据工具链支持和系统需求选择。

1. 前处理：让输入符合模型的约定

视觉模型的前处理通常包括图像缩放、裁剪或填充、颜色通道转换、归一化，以及数据类型和张量布局调整。

对于机器人控制策略，输入还可能由关节位置、关节速度、IMU 数据和历史动作组成。这时需要对齐观测顺序、单位、坐标系和归一化参数。

部署时的数据处理，应与训练和验证阶段为模型约定的方式保持一致。 输入尺寸正确，只是其中一个条件。

例如：训练时使用 RGB 图像，部署时却直接传入 BGR 数据，程序可能照常运行，识别效果却会明显变差。

2. 推理：CPU、GPU 与 NPU 分工协作

CPU 通常承担系统调度、通信和业务逻辑，也可以执行模型计算；GPU 擅长并行计算；NPU 则面向神经网络计算进行专门优化。前后处理同样可能根据平台能力交给不同硬件执行。

应用程序通过运行时加载模型、准备输入、提交计算并取得输出。需要检查哪些算子实际进入了加速器，以及数据传输和同步是否引入额外开销。

模型加载成功，只能说明运行链路走通了一部分。 输出是否正确、是否用上预期的计算硬件、持续运行是否稳定，还要分别验证。

3. 后处理：把模型输出变成可用结果

模型输出通常还需要解释和转换。目标检测可能需要解码预测框、筛选置信度、进行非极大值抑制（NMS）并还原坐标；控制策略则可能需要按训练时的动作定义进行缩放和接口转换。

例如：策略网络输出归一化的关节动作后，还要恢复到约定的物理量，并结合关节限位、速度或力矩限制，交给控制器执行。

前处理和后处理都是模型应用的一部分，任何一处约定不一致，都可能让正确的网络产生错误的系统行为。

4. ROS2：让推理结果参与模块协作

机器人通常同时运行摄像头、雷达、定位、规划和控制等模块。ROS2 通过节点、话题等通信机制，让这些模块交换数据。

推理程序可以封装为一个节点：订阅传感器数据，执行前处理、推理和后处理，再发布结果，供其他节点使用。

例如：摄像头节点发布图像，推理节点发布障碍物检测结果，规划模块结合其他传感器信息选择路线，控制模块据此驱动机器人。

在这条链路中，ROS2 组织通信，推理引擎负责模型计算，应用程序负责数据和接口的衔接。选择消息格式、时间戳、坐标系和队列策略时，也要考虑下游模块能否及时使用结果。

硬件资料里常见的“核心板”和“开发板”也可以放在这里理解：核心板通常集成主要计算资源，开发板还提供便于调试的电源和外设接口；产品中也可能采用核心板配合专门设计的载板。

六、实机验证

板端验证需要同时观察模型和整个机器人系统：

验证维度 需要关注的内容
正确性 原模型、导出模型、板端模型在相同输入下的输出差异，以及独立测试集上的任务指标
实时性 完整链路时延、时延波动、数据积压，以及结果是否仍然及时
资源开销 内存峰值、CPU 与加速器负载、功耗和温度
稳定性与任务效果 长时间运行、异常输入，以及真实场景中的感知或控制表现

尤其要区分单次模型推理耗时和完整链路时延。从数据就绪到结果可用，还可能经历排队、前处理、数据搬运、后处理和通信。采用流水线时，各阶段可能重叠，最终应测量实际的端到端时延。

例如：一个要求每 20 ms 更新一次、且需在周期内完成的决策环节，即使模型推理只用 10 ms，也要为数据处理和通信留出时间。

平均速度同样不能代替稳定性。少数明显变慢的周期、持续积压的消息，或者设备升温后的降频，都可能影响机器人的响应。

模型指标还需要结合任务场景理解：整体检测精度变化较小，并不保证关键障碍物上的表现也保持不变。

例如：量化后整体检测精度只下降一点，但近距离细小障碍物的漏检变多，机器人避障的可靠性就可能受到明显影响。

总结

理解这些概念以后，可以围绕一个小模型，把整条链路逐步跑通：先建立原模型的精度基线，再导出并对照输出；随后在目标设备上运行，测量性能并决定是否需要优化；最后接入 ROS2，验证实际任务表现。

每前进一步，都保留一份可比较的结果。出现偏差时，就能沿着模型导出、输入处理、量化、硬件执行和系统通信逐段定位。

这也是端侧部署最有价值的地方：把模型在训练环境里获得的能力，落实为机器人在真实环境中能够持续使用的能力。
