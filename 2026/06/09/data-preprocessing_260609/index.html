建模前的数据预处理超全流程

发表于2026-06-09|更新于2026-09-03|数据分析
|总字数:5.9k|阅读时长:17分钟|浏览量:

前言：为什么预处理决定模型上限 🔍

假设我们现在真的要做一个模型，我觉得第一件事不是马上想用随机森林、神经网络还是别的什么算法，而是先问一句：这份数据真的靠谱吗？

模型的本质其实很简单，就是从数据里学习规律。
所以如果数据本身有问题，比如字段口径不清楚、缺失值很多、单位混在一起、同一个对象被重复记录，那模型最后学到的可能就不是业务规律，而是数据采集和填报过程中的各种坑。

很多时候我们会觉得“数据预处理”就是把空值补一下、把异常值删一下、把格式统一一下。但我会更愿意把它理解成：在建模之前，先判断这批数据到底能不能用。

简单来说，预处理要让数据具备三个条件：

  1. 可信：我知道数据从哪里来、什么时候来的、每个字段是什么意思。
  2. 可用：缺失、异常、重复、单位、编码这些问题，都被检查过、处理过或者至少标记过。
  3. 可解释：我知道为什么这样处理，别人问起来也能说清楚，而不是“我感觉这样比较好”。

建模前的数据预处理，其实可以按下面这个顺序来做：

这里要注意一下，这个流程不是做完一步就永远不回头了。
比如我们在 EDA 的时候发现某个字段分布特别奇怪，就可能要回到前面重新检查异常值；发现某些类别写法不统一，也可能要回去补一条清洗规则，所以它更像一个循环。

阶段 核心问题 关键产出
原始数据备份 原始数据能否回溯 raw 数据、版本日志
字段口径确认 每个字段到底代表什么 数据字典、样本粒度说明
数据质量扫描 数据是否可信可用 质量检查表
问题清单整理 问题在哪里、严重到什么程度 缺失、重复、异常、口径问题清单
预处理规则制定 怎么处理才有依据 清洗和转换规则
执行预处理 如何落到可复现的数据集 processed 数据、处理脚本
效果验证 处理是否改变数据结构 处理前后对比报告
EDA 数据呈现什么规律 描述统计与可视化结果
数据准入判断 是否可以进入建模 可用、谨慎使用、暂不使用字段清单

1. 原始数据备份 📦

拿到数据以后，不建议直接在原始文件上改。而是，先进行数据备份，保证所有处理都在副本或者脚本生成的中间数据上进行。

这个习惯看起来很小，但真的很重要。因为后面如果发现结果不对，我们必须能回到最开始的数据版本，看看问题到底是原始数据就存在，还是我们处理过程中引入的。

推荐建立如下目录：

每个数据批次最好都记录清楚：数据来源、时间范围、样本粒度、主键字段、更新频率、责任人和版本号。

原始数据永远不要直接改。真正可靠的预处理流程，应该能从 raw 数据一键复现到 processed 数据。

2. 数据结构理解与字段口径确认 🧩

第二步是理解数据。

我们至少要先把下面几个问题弄清楚：

问题 说明
一行代表什么 是一个对象、一次事件、一个项目，还是一个时间点
主键是什么 是否能唯一识别一条样本，是否存在重复或缺失
字段是什么意思 字段名称、中文含义、数据类型、单位和计算口径是否明确
表之间如何关联 主表、明细表、维表之间是一对一、一对多还是多对多

这一步最好能整理出一个数据字典。数据字典不用一开始就特别复杂，但至少要包括字段名、业务含义、数据类型、单位、合理取值范围、是否必填、缺失代表什么、统计口径是什么。

这里我想重点说一下样本粒度。
样本粒度就是“一行数据到底代表什么”。比如一张表一行代表一个项目，另一张表一行代表一个项目的某个月，如果直接关联，项目就可能被月份重复放大。

3. 数据质量扫描 🩺

理解完字段以后，就可以开始检查数据质量了。
这里不要只看“有没有空值”，因为数据问题远远不止缺失值。一个比较完整的检查，至少可以从四个层面来看：表级、字段级、记录级、关系级。

3.1 表级检查

表级检查就是先看整张表本身有没有明显问题。比如表是不是齐全，行数列数是不是符合预期，时间范围有没有覆盖我们要分析的周期。

检查项 关注点
表数量 是否符合预期，是否有缺表或重复表
行数列数 样本量和字段数量是否异常
时间范围 是否覆盖分析所需周期
主键质量 主键是否缺失、重复或冲突
表间关联 不同表能否通过主键或外键稳定匹配

3.2 字段级检查

字段级检查就是看每一个变量能不能用。这个时候我们会开始碰到很多很真实的问题：

  1. 字段类型是否正确，例如日期是否被读成文本。
  2. 单位是否统一，例如元、万元、亿元是否混用。
  3. 数值字段是否存在非法值，例如负成本、比例超过 100%。
  4. 类别字段是否存在拼写不一致，例如“北京”“北京市”“BJ”。
  5. 关键字段缺失率是否在可接受范围内。

我建议这里输出一个字段画像表，后面做报告或者复查都会方便很多：

字段 类型 缺失率 唯一值数量 最小值 最大值 异常说明

3.3 记录级检查

记录级检查就是看每一行样本是不是合理。比如有没有完全重复的记录，同一个主键是不是出现了多条冲突记录，一行里面是不是很多字段都缺失，开始时间是不是晚于结束时间，总量是不是小于分项之和。

3.4 关系级检查

关系级检查就是看多张表之间能不能对得上。
比如主表和明细表能不能匹配，汇总值是不是等于明细值之和，同一个字段在不同系统里是不是同一个口径，多表连接以后样本数有没有突然变多。

如果你的分析依赖多张表，那这一步非常重要。因为单张表看起来都没问题，不代表连接以后还没问题。

4. 问题清单整理 📝

质量扫描之后，不要只写一句“数据质量一般”。
我们要把问题整理成一张清单，写清楚问题是什么、出现在哪里、严重不严重、准备怎么处理。

问题类型 典型内容 输出结果
缺失值 空值、特殊缺失编码、分组缺失 缺失率表、缺失模式图
重复值 完全重复、主键重复、业务重复 重复样本清单
异常值 录入错误、单位错误、真实极端值 异常规则与异常样本表
口径问题 单位混用、计算规则不一致 字段口径问题表
关联问题 外键缺失、一对多膨胀、汇总不一致 多表关系检查表

这一步最重要的是区分：哪些是真的错误，哪些只是看起来奇怪但其实有业务意义。
比如极端值可能是录入错误，也可能是真实存在的高风险样本；缺失值可能是没填，也可能代表“不适用”或“没有发生”。如果不先判断原因，后面很容易把有价值的信息清洗掉。

判断原则：先判断问题性质，再决定处理方式。“可疑数据”不直接等同于“错误数据”。

5. 预处理规则制定 🛠️

有了问题清单以后，我们需要先制定规则，再进行处理。

因为数据预处理非常不推荐“边看边改”，今天觉得这个值奇怪就删掉，明天觉得那个字段缺失就填个均值。这样过程不可复现，也说不清楚为什么这么处理。

规则最好满足三个原则：

  1. 可解释：每一项处理都有业务或统计依据。
  2. 可复现：规则能被脚本重复执行，而不是依赖手工记忆。
  3. 可追溯：保留原始值、处理规则、处理时间和处理后结果。

比如缺失值不能统一用均值填补，异常值也不能统一删除。不同字段的重要性不同，缺失原因不同，后续分析目标也不同，所以处理方式也应该不同。

另外，如果后面要建模，一定要注意数据泄漏。
简单来说，就是不要让模型提前看到它本来不该看到的信息。比如不能先用全量数据计算均值、标准差、分位数或者目标编码，再划分训练集和测试集。应该是，只在训练集上拟合插补器、编码器和标准化器，再应用到验证集或测试集。

6. 执行清洗、转换、插补、编码和标准化 ⚙️

这一部分才是数据处理的部分。我们可以把这部分拆成五类：清洗、转换、插补、异常处理、编码和标准化。

6.1 清洗与格式解析 🧹

基础清洗的目标很朴素：先让数据能被稳定读取、稳定处理。常见操作包括：

  1. 去除字段名前后的空格、特殊符号和不可见字符。
  2. 统一字段命名规则。
  3. 删除完全空列和无意义索引列。
  4. 将“1,000”“￥1000”“15%”“2024/01/01”等文本转换为标准数值或日期。
  5. 统一编码格式，避免中文乱码。
  6. 处理 Excel 合并单元格、隐藏列和异常表头。

6.2 转换与单位统一 🔄

数据转换不只是把格式变好看，更重要的是统一口径。比如金额到底是元还是万元，百分比到底是 15% 还是 0.15，这些如果不统一，后面的统计结果会直接错。

常见转换包括：

原始形式 目标形式 注意事项
文本日期 日期类型 处理非法日期、默认日期和时区
百分数字符串 数值类型 统一 15% 与 0.15 的表达
金额文本 数值类型 去除逗号、单位和货币符号
类别编码 类别类型 保留编码对应含义
是/否、Y/N、1/0 布尔类型 统一映射规则

6.3 缺失值分析与插补 🧮

缺失值处理的第一步，是先把“什么算缺失”定义清楚。
缺失不一定只表现为 NULL 或 NaN，还可能是空字符串、-、/、未知、未填、999、9999，甚至在某些字段里，0 也可能代表缺失。

在真正处理缺失之前，我们还要理解三种缺失机制：

缺失机制 含义 处理思路
MCAR 完全随机缺失 缺失与已观测和未观测变量都无关 少量缺失可删除或简单插补
MAR 随机缺失 缺失可由其他已观测变量解释 可考虑分组插补、回归插补、多重插补
MNAR 非随机缺失 缺失与缺失值自身或未观测因素有关 需业务调查、缺失标识和敏感性分析

记忆方式：MCAR 像“随机丢”，MAR 像“有规律地缺但规律可解释”，MNAR 则是“缺失本身就携带重要信息”。

常见处理方法包括删除样本、删除字段、均值或中位数插补、众数插补、分组插补、回归插补、KNN 插补、多重插补，以及添加缺失标识变量。

这里有几个经验原则：

  1. 目标变量缺失，通常不建议硬插补后再拿去做监督建模。
  2. 关键业务字段缺失，优先回源补数，不要一上来就算法插补。
  3. 插补以后一定要看分布有没有明显变化。

如果缺失情况比较复杂，可以考虑 MICE 多重插补。它不是简单填一个确定值，而是为每个有缺失的变量建立插补模型，通过多轮迭代生成多套完整数据集，再合并分析结果。它比均值插补更能反映不确定性，但也不是万能的，尤其对 MNAR 这种非随机缺失仍然要谨慎。

6.4 异常值识别与处置 🚨

异常值这部分也很容易被误解。
很多人看到一个值特别大或者特别小，就想直接删掉。但其实异常值至少可以分成三类：

  1. 错误异常：由录入、单位、采集或系统错误造成，应修正或剔除。
  2. 真实极端值：虽然偏离总体，但具有真实业务含义，应保留并标记。
  3. 影响性样本：对统计关系或模型结果影响过大，需要进一步诊断。

常用检测方法包括业务规则、箱线图/IQR、Z-score、MAD、分位数法、散点图、聚类或距离方法、时间序列分解等。对于多变量数据，还可以用马氏距离、Local Outlier Factor、Isolation Forest、One-Class SVM 或聚类距离。

但是区分是异常数据还是错误数据，需要根据情况选择修正、删除、缩尾、分箱、对数转换，或者保留原值并添加异常标识。

6.5 重复值、一致性与编码标准化 🧱

重复值也不只是一样这么简单。
它可能是完全重复，也可能是主键重复、近似重复，甚至是同一个业务事件被多个系统各记了一次。

完全重复记录通常保留一条；主键重复可以按时间、版本或数据来源优先级处理；近似重复和业务重复就需要结合规则或者人工确认。

一致性校验应覆盖：

类别变量处理前，先要统一表达。比如“北京”“北京市”“BJ”“beijing”其实可能都是同一个意思。如果不先归并，后面做统计或者编码时就会被当成不同类别。

统一之后，再根据建模需要选择 One-hot 编码、序数编码、频数编码、目标编码或者低频类别合并。这里尤其要注意：目标编码必须只在训练集内计算，不然很容易泄漏。

数值变量则要根据分布和模型需要选择标准化方法：

如果变量明显右偏，比如金额、规模、持续时间这类字段，还可以考虑对数转换。这个操作不是为了“让数据变漂亮”，而是为了让后续统计和模型更稳定。

7. 处理效果验证 ✅

处理完以后，不要只输出一张“清洗后数据表”就结束。
我们还要检查：处理有没有真的解决问题？有没有顺手把数据结构改坏？

建议从下面这些角度做处理前后对比：

验证内容 目的
行数、列数变化 检查是否误删样本或字段
缺失率变化 确认缺失处理是否有效
均值、中位数、标准差变化 判断是否改变总体分布
类别占比变化 判断是否引入类别偏差
异常值数量变化 评估异常处理效果
相关性变化 检查处理是否改变变量关系
训练/测试分布差异 判断后续模型是否稳定

如果清洗后均值、中位数、分布形态或者类别占比发生明显变化，一定要解释原因。
预处理的目标是提高数据可用性，不是人为制造一份看起来更“规整”的数据。

8. 探索性数据分析 📊

探索性数据分析，也就是 EDA，它帮我们更直观的看出来，数据长什么样？有什么问题？变量之间有没有关系？它到底支不支持后续分析？

8.1 单变量分析

单变量分析就是先一个字段一个字段看。
数值变量可以看样本数、缺失率、均值、中位数、标准差、最小值、最大值、分位数、偏度、峰度、长尾分布和异常值。常用图形包括直方图、密度图、箱线图和 Q-Q 图。

类别变量则要看类别数量、各类别频数和占比、低频类别、拼写或编码不一致，以及类别是否极度不平衡。常用图形包括条形图和帕累托图。

8.2 双变量与多变量分析

双变量分析就是看两个变量之间有没有关系。可以按变量类型来选方法：

变量组合 常用方法
数值变量与数值变量 散点图、相关系数、局部平滑曲线
数值变量与类别变量 分组箱线图、分组均值和中位数
类别变量与类别变量 交叉表、卡方检验、堆叠条形图

多变量分析可以使用相关性矩阵、散点图矩阵、主成分分析、聚类分析、热力图和分面图。
这里要注意共线性：如果多个变量高度相关，后续建模或者权重分析中可能会重复计算同一类信息。

8.3 时间与分组分析

如果数据包含时间字段，就要检查时间是不是连续，有没有缺口，有没有季节性、趋势变化或者结构突变。做预测任务时尤其要小心，不能把未来信息混进训练数据里。

分组分析也很有用，因为总体均值经常会掩盖组间差异。
比如按照时间、地区、类型、来源、规模、风险等级分组以后，可能会发现某些异常只集中在某一类样本里。如果不同组的分布差异很明显，后面可能就需要分组建模或者分组设置规则。

9. 数据准入判断 🚦

完成质量检查、预处理和 EDA 以后，最后一步就是判断：这批数据能不能进入建模阶段。

这里不要默认“处理完了就能建模”。有些数据虽然已经清洗过，但核心字段缺失太严重、目标变量口径不统一、历史数据和未来应用场景差异太大，这种情况下就应该先暂停，而不是硬上模型。

可以从下面这些标准来判断：

判断项 准入要求
样本量 满足分析目标和分组分析需要
字段完整性 核心字段缺失率可控
口径一致性 关键字段定义和单位统一
异常值 已识别、处理或标记
目标变量 定义清楚，缺失和异常可解释
时间范围 能覆盖分析所需周期
分布稳定性 不存在无法解释的严重漂移
数据泄漏风险 已识别并排除明显泄漏字段
可追溯性 原始数据、处理规则和版本可追溯

如果出现核心字段缺失严重且无法补充、目标变量口径不统一、样本量明显不足、多表关联大量冲突、异常值无法判断真伪且占比高、历史数据与未来应用场景明显不一致，或者处理过程不可复现，就应该暂缓模型选择。

准入结果可以分为三类：

字段等级 含义 建议
可直接使用字段 质量较好，口径明确 进入后续分析
谨慎使用字段 存在缺失、异常或口径问题，但仍有价值 标记问题，做敏感性分析
暂不使用字段 质量不足或含义不清 等待补数或口径确认

落地执行清单 📌

如果真的要把这套流程落到项目里，我觉得可以直接用下面这张清单。
每做完一项，就留下对应的输出结果，后面写报告或者复盘都会轻松很多。

阶段 具体操作 输出结果

✅ 字段解析 统一字段名、类型、编码和格式 字段解析报告
✅ 主键检查 检查主键缺失、重复和冲突 主键质量表
✅ 粒度确认 明确一行代表的对象或事件 样本粒度说明
✅ 缺失识别 统一 NULL、空字符串、特殊缺失编码 缺失值映射表

小结 ✨

数据预处理主要是在判断这批数据有没有资格被拿去建模。

🥳个人理解：模型当然很重要，但如果数据来源不清楚、字段口径不一致、缺失和异常解释不了、处理过程也复现不了，那后面换再复杂的模型也只是把问题包装得更高级了一点。真正靠谱的分析，应该是从一份能被解释、能被追溯、能被复现的数据开始的。
